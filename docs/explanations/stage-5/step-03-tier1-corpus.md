# Stage 5, Component 3 (part 1) — Tier-1 local corpus: ingestion and retrieval

## 1. What this component does

This is Tier 1 of tiered RAG grounding: a curated, versioned list of real
papers (`data/corpus/paper_list.json`) gets turned into searchable content —
fetched (or, for most entries, confirmed already fetched by a human),
extracted, chunked, embedded, and stored in Postgres — and a retrieval
function (`retrieve_local`) turns a plain-text query into the most
semantically relevant chunks, ranked by cosine similarity.

**What this explicitly does not cover, on purpose:** Tier 2 (whitelist
search via Tavily) and the mechanical escalation between tiers are a
separate, later piece of work — this component proves Tier 1 alone, cleanly,
before anything else builds on top of it. No LLM call happens anywhere in
this component either; ingestion is pure fetch/extract/chunk/embed, and
retrieval is a pure vector-similarity query. Both are exactly the kind of
deterministic, build-time/offline work `docs/architecture.md` describes for
grounding infrastructure — the LLM only ever sees the *output* of retrieval
(as context in a later prompt), never touches ingestion or search itself.

## 2. Every meaningful line explained

### The schema fix (`agentic_core/db/models.py`)

`CorpusPaper.id` replaced `CorpusPaper.arxiv_id` as the primary key, and a
new `fetch_path` column was added. This was necessary, not cosmetic: the
committed `paper_list.json` has 15 real papers, and only one of them
(`chen_zimmermann_2022`) is actually on arXiv — the strongest, most
foundational papers (Poterba & Summers, Fama & French, Lakonishok/Shleifer/
Vishny, Harvey/Liu/Zhu, and others) predate arXiv's finance coverage
entirely and live on NBER or SSRN instead. A schema whose primary key is
literally called `arxiv_id` can't represent that. The fix uses
`paper_list.json`'s own `id` field (a human-readable slug like
`"poterba_summers_1988"`) as the key for every paper regardless of where it
came from — even `chen_zimmermann_2022`, the one arXiv-native entry, uses a
slug rather than its raw arXiv ID (`2209.13623`) as its `id`; the real arXiv
ID only appears inside its `url` field, parsed out at fetch time.

`corpus_papers` deliberately stays thin: `id`, `title`, `fetch_path`,
`fetched_at`, `raw_path`. Everything else in `paper_list.json` — `authors`,
`year`, `effect_family`, `grounds`, `note` — is *not* duplicated into
Postgres. `paper_list.json` is the one source of truth for curation
metadata; anything needing a full citation later (Component 4, most likely)
reads the JSON file directly rather than a second copy that could silently
drift out of sync with it.

Applying this required a real Alembic migration (`401a5c77cf08`), and
reviewing the autogenerated version before running it caught a real bug in
what autogenerate produced — covered in section 3.

### `CorpusEffectFamily` (`agentic_core/schemas.py`)

`paper_list.json` tags two papers (`harvey_liu_zhu_2016`,
`chen_zimmermann_2022`) with `effect_family: "methodology"` — neither is
about a specific effect a hypothesis would investigate; both ground the
*system's own* statistical rigor (the multiple-comparisons correction). Since
Component 2's `EffectFamily` enum backs `ParsedCharter.hypothesis_families`
— the field she fills in by describing what she wants investigated —
"methodology" has no business being a value there; nobody would ever mandate
"investigate methodology." A new type, `CorpusEffectFamily = EffectFamily |
Literal["methodology"]`, gives the corpus its own, slightly wider tag set
without polluting the charter-facing enum with a value that should never
appear in a charter.

### `agentic_core/corpus.py`

`_arxiv_id_from_url` extracts the real arXiv ID from a `url` field like
`"https://arxiv.org/abs/2209.13623"` via regex, rather than expecting
`paper_list.json` to carry a separate `arxiv_id` field — matching how the
committed file is actually shaped (it doesn't have one).

`_fetch_arxiv_pdf` calls the real arXiv API (`arxiv.Client().results(...)`)
to confirm the paper genuinely exists *before* downloading anything — if
`chen_zimmermann_2022`'s `url` had a typo'd or stale ID, this raises here,
loudly, rather than silently downloading nothing or (worse) the wrong paper
under the right filename. The actual PDF URL comes from the API result's own
`links` list, filtered to `content_type == "application/pdf"` — the
installed `arxiv` package (4.0.1) turned out not to have the
`download_pdf()` convenience method older versions had; this was discovered
by inspecting the installed package directly (`dir(arxiv.Result)`) rather
than writing code against a remembered API and finding out at runtime.

`_extract_text` joins `pypdf`'s per-page text, then strips literal NUL
bytes. This second step didn't exist in the first version of this function —
it was added after a real ingestion run failed with `ValueError: A string
literal cannot contain NUL (0x00) characters.` on one of the five real NBER
PDFs. Postgres's `text` type cannot store `\x00` at all, not as an escaping
problem but as a hard storage limitation — pypdf can legitimately produce
one from certain PDFs' internal encoding. This is the same *category* of
limitation the original plan already disclosed ("math and tables will
extract noisily") — not a new, unanticipated kind of problem, just a second
concrete instance of the same one.

`_chunk_text` uses `RecursiveCharacterTextSplitter` with `length_function`
set to a real `tiktoken` encoder (`cl100k_base`), not character-count
approximation — so `chunk_size=500` genuinely means ~500 tokens, matching
what the original plan committed to, rather than "500 characters, which is
roughly 125 tokens and not what was promised."

`embed_query` prepends `"Represent this sentence for searching relevant
passages: "` to the query text before embedding; `ingest_paper` embeds
chunk text with no prefix at all. This asymmetry is deliberate and
load-bearing, not an inconsistency: `BAAI/bge-small-en-v1.5` is trained for
*asymmetric* retrieval, where only the query side gets an instruction
prefix. Applying it to both sides, or neither, doesn't raise an error — it
just quietly makes retrieval worse, which is exactly the kind of mistake
that's easy to ship unnoticed. Stated here so it isn't rediscovered later.

`ingest_paper`'s dispatch on `fetch_path` is the component's central control
flow — four branches, each returning a structured `IngestOutcome` rather
than silently succeeding or silently doing nothing:
- `"citation_only"` → always skipped, permanently. No accessible full text
  exists, so there is nothing to embed — these two papers (De Bondt-Thaler,
  Rozeff-Kinney) can never appear in `retrieve_local`'s results, by design.
- `"manual_needs_confirmation"` → always skipped. Provenance for this one
  entry (Bouman & Jacobsen) isn't verified yet, so nothing gets placed or
  ingested until it is — a different reason for "not yet" than the next
  case, and reported with different wording so the two aren't confused.
- `"manual"` → checks `data/corpus/raw/<id>.pdf`. Present → ingest. Absent →
  skip with a message naming the expected path and echoing the entry's own
  `source`/`url` fields, so acting on the message doesn't require re-opening
  `paper_list.json`.
- `"arxiv"` → auto-fetches via `_fetch_arxiv_pdf`, unconditionally (no local
  file to check first).

The idempotency check (`session.get(CorpusPaper, paper_id)`) happens before
any of this dispatch, for every fetch_path — a paper already in
`corpus_papers` is reported as `already_ingested` and nothing downloads,
re-extracts, or re-embeds, regardless of which fetch path it came from.

`retrieve_local` builds `CorpusChunk.embedding.cosine_distance(query_vec)`
— pgvector's `<=>` operator, exposed through the SQLAlchemy `Vector` type's
comparator — orders ascending (smallest distance = most similar), and
reports `relevance = 1.0 - distance` so callers see an intuitive
"higher is better" number rather than pgvector's own distance convention.
A plain sequential scan, no `ivfflat`/`hnsw` index — at 612 real chunks
right now, and a few thousand at full corpus size, indexed approximate
search buys nothing an exact scan doesn't already give for free (this was
flagged as the expected scale back in step-01, before any real data existed
to confirm it against; it's now confirmed against real data).

## 3. Design decisions and rejected alternatives

### Catching autogenerate's own bug in the corpus_papers migration, before running it

Alembic's `--autogenerate` produced a migration that would have failed
outright: it dropped `arxiv_id` (the old primary key), added a plain `id`
column with *no* primary key constraint, and then tried to create a foreign
key from `corpus_chunks.paper_id` straight to it. Postgres rejects a foreign
key whose referenced column has no unique or primary-key constraint — this
migration, run as generated, would have errored on `alembic upgrade head`
rather than doing anything destructive, but it would still have blocked the
whole component on a bug in generated code rather than hand-written code.
The alternative — trusting autogenerate's output the way `alembic revision
--autogenerate` boilerplate literally invites ("please adjust!" is printed
in every generated file, a standing reminder this step isn't meant to be
skipped) — was rejected the same way it was in step-01's own two hand-fixes:
autogenerate is a diffing tool, not a correctness guarantee, and this
project's own established habit is to read every generated migration before
running it. Fixed by reordering (add the new columns and drop the old one
first, explicitly create the primary key, only then create the foreign key)
and mirroring the same fix in `downgrade()`.

### An explicit `session.flush()` instead of trusting the ORM's default insert ordering

The real bug, reproduced in isolation with a single `CorpusPaper` and a
single `CorpusChunk` before touching real ingestion data: `session.add()`
called in the correct order (paper, then its chunks), followed by one
`session.commit()`, still produced `ForeignKeyViolation: ... paper_id
... is not present in table "corpus_papers"`. SQLAlchemy's unit-of-work is
supposed to topologically sort pending inserts by foreign-key dependency
even without an explicit ORM `relationship()` connecting the two mapped
classes — that's the documented default behavior — but it didn't happen
here. Rather than chase down *why* (a genuinely interesting question, but
not one that changes what the fix needs to be), the fix taken was the
direct one: `session.flush()` right after adding the `CorpusPaper`, forcing
its `INSERT` to actually execute — visible within the same transaction —
before any `CorpusChunk` row referencing it gets added. This is strictly
more reliable than depending on implicit ordering behavior that had just
been observed, empirically, not doing what its own documentation promises
in this specific case. The alternative — adding an ORM `relationship()`
between `CorpusPaper` and `CorpusChunk` specifically to give the unit-of-work
a graph edge to infer the dependency from — was considered and rejected:
Component 1 already deliberately chose plain foreign-key columns over ORM
relationships everywhere in this schema, reasoning that the FK chain here
is closer to a linear sequence than a "parent with many uniform children"
pattern relationships are meant for; adding one relationship as a workaround
for this specific ordering bug would reintroduce exactly the pattern that
was deliberately avoided, for a problem an explicit `flush()` solves just as
well with no schema-level change at all.

### Stripping NUL bytes once, at the extraction boundary, not at every call site

The alternative — catching the `ValueError` at the point of insertion and
retrying with sanitized text — was rejected as solving the same problem in
a more roundabout way: it would mean every future caller of `_extract_text`
needs to remember this failure mode and handle it, whereas fixing it once,
at the function that produces the raw text, means nothing downstream ever
needs to know NUL bytes were ever a possibility. This mirrors the project's
existing instinct (Component 1's own JSONB/typed-column line, `llm_client`'s
single validation boundary) to put a defense at the one place responsible
for it, not scattered wherever it happens to bite.

## 4. Concepts introduced

**Asymmetric embedding retrieval.** Some embedding models (like
`bge-small-en-v1.5`) are trained specifically for retrieval, where a short
query and a long passage aren't expected to look alike in embedding space
the way two similar sentences would — the model is trained knowing one side
is a *question about* the other, not a paraphrase of it. The practical
consequence: these models expect an instruction prefix on the query side
only, and applying it inconsistently doesn't error, it just silently
degrades match quality. This is a genuinely different failure mode from most
bugs in this project so far — nothing crashes, nothing looks wrong in a
quick smoke test, the numbers just get worse in a way that's easy to miss
without a query like the three run in section 5 that has an unambiguous
right answer to check against.

**Why an ORM's automatic dependency ordering isn't something to lean on
blindly.** SQLAlchemy's unit-of-work is *supposed* to insert rows in an
order that respects foreign-key dependencies, even without a `relationship()`
telling it the two tables are related. This component found a real case
where that didn't happen. The lesson generalizes beyond this one bug:
"the ORM handles ordering automatically" is a property of the common case,
not a guarantee — for anything cross-table and dependency-sensitive, an
explicit `flush()` at the dependency boundary is a small, cheap way to stop
depending on that guarantee holding.

## 5. How this component was verified

Every claim was checked against something real, not the design reasoning
alone. The corpus_papers migration was generated against the real
`strategy_research` database, read in full before running (which is what
caught the missing-primary-key bug before it could fail at
`alembic upgrade head`), and applied to both databases — `\d corpus_papers`
and `\d corpus_chunks` confirmed the real resulting schema, not just the
migration's own claimed intent.

Both real bugs were reproduced in minimal isolation *before* being
considered understood, and re-verified in the same isolation *after* the
fix, before either fix was trusted against real ingestion data: the FK
ordering bug with a single hand-constructed `CorpusPaper` + `CorpusChunk`
pair (failed, then succeeded after adding `flush()`); the NUL-byte issue was
caught directly by the real pipeline's own error message naming the exact
failure, then fixed and re-run.

The full pipeline was run for real against all 15 `paper_list.json` entries,
twice (once before, once after the two fixes) — 6 of 6 downloads that had a
locked-in URL succeeded (5 manual PDFs fetched by curl earlier in this
session, one arXiv paper auto-fetched for real by this component's own
code), producing 612 real chunks across 6 papers, confirmed directly against
the database (`SELECT id, fetch_path, fetched_at FROM corpus_papers`,
`SELECT paper_id, COUNT(*) FROM corpus_chunks GROUP BY paper_id`), not just
the ingestion script's own printed claims. Re-running after both papers were
already ingested confirmed idempotency for real: both reported
`already_ingested` rather than re-downloading or re-embedding.

Retrieval was proven with three real queries against the real, mixed
(4-topic, 6-paper) corpus: "multiple hypothesis testing significance
threshold for new factors" → all three top results from
`harvey_liu_zhu_2016`; "mean reversion in stock prices" → all three from
`poterba_summers_1988`; "low beta stocks outperform" → all three from
`frazzini_pedersen_2014`. Every query landed exclusively on its
semantically correct paper out of six real candidates spanning four
different topics — evidence the embedding space is actually capturing
meaning, not coincidentally matching keywords (none of the three queries
literally repeats the paper titles' own wording).

**What this does not prove.** Only 6 of the 15 real entries are actually in
the retrievable corpus right now — 6 manual papers are still waiting on a
locatable direct-PDF URL, one (Bouman & Jacobsen) is waiting on provenance
confirmation, and two (De Bondt-Thaler, Rozeff-Kinney) will never be
retrievable at all. The three retrieval queries were chosen because their
correct answer was already known (each maps unambiguously to exactly one of
the six ingested papers) — this proves the mechanism works on cases with an
obvious right answer, not that it will rank sensibly on a genuinely
ambiguous query spanning multiple plausible papers, which hasn't been tested
here. And `paper_list.json` itself has an open, unresolved question as of
this component: it has 15 entries, not the 14 stated when it was described
as finalized — specifically due to `da_liu_schaumburg_reversal`, a real,
well-formed third mean-reversion source with `year: null`. Whether that's an
intentional addition (in which case the year should be filled in) or an
accidental inclusion is not this component's call to make, and it hasn't
been resolved as of this writeup.

## 6. Interview defense

**Q: Why didn't you just trust `alembic revision --autogenerate`'s output
for the corpus_papers migration, the way most of that file's DDL really is
autogenerated correctly?**

A: Because "usually correct" isn't "always correct," and this is a case
where the boilerplate comment autogenerate prints into every file it
generates — "please adjust!" — turned out to be load-bearing advice, not
a formality. Autogenerate diffs Python model metadata against live database
state; it has no concept of "this column used to be a primary key and needs
a replacement one," so it produced DDL that would create a foreign key
pointing at a column with no uniqueness guarantee at all. Reading the
generated file before running it — the same habit already established in
step-01 for a different reason (a missing import, a missing `CREATE
EXTENSION`) — is what caught this before it could fail against a real
database.

**Q (hard): You found a case where SQLAlchemy's own documented automatic
FK-ordering behavior didn't hold. Doesn't that mean there could be *other*
places in this codebase — Components 1 and 2's own inserts — silently
relying on the same guarantee, that just haven't been unlucky enough to hit
it yet?**

A: This is a fair, uncomfortable question, and the honest answer is: yes,
that's a real, live risk, not fully closed by this component's own fix.
Component 1 and 2's insert patterns (`Charter` alone, `Hypothesis` alone,
one row at a time, never two related mapped classes added and committed
together in the same flush) never actually exercise the exact condition
that broke here — `CorpusPaper` and `CorpusChunk` inserted together, in the
same transaction, with a foreign key between them and no `relationship()`
declared. That's a structural reason to believe those components are safe,
not a guarantee — it wasn't independently re-verified as part of this
component, since doing so would mean re-testing components already closed
and signed off on their own terms. The concrete, checkable claim this
component supports is narrower: this specific pattern (`session.add(parent)`
then `session.add(child, ...)` then one `commit()`, no `relationship()`) is
now known not to be safe to assume, and the fix (`flush()` at the boundary)
is applied everywhere in Stage 5 that pattern actually occurs so far — which
is only here.

**Q: Why didn't you just use character-count chunking instead of pulling in
`tiktoken` as a length function — wouldn't ~2000 characters have been close
enough to ~500 tokens?**

A: Because "close enough" wasn't the commitment made. The original plan
stated ~500-token chunks specifically, and English text (especially
academic prose full of numbers, hyphenated terms, and citations) doesn't
convert to tokens at a clean, stable ratio — using an actual tokenizer as
the splitter's length function is barely more code than a character-count
approximation (one `length_function` argument) and means the number
actually means what it claims to mean, rather than being an approximation
that happens to usually be roughly right.

**Honest weaknesses, stated plainly:** 9 of 15 real papers aren't in the
retrievable corpus yet (6 needing a URL, 1 needing confirmation, 2 never
retrievable at all) — Tier 1 grounding right now covers 4 of 6 effect
families plus methodology, not the full charter-facing family list, and
`low_volatility`/`value` have only one paper each actually ingested despite
`paper_list.json` intending two apiece. The `da_liu_schaumburg_reversal`
count discrepancy is still open, unresolved as of this writeup. And the ORM
ordering bug's blast radius beyond this one component was reasoned about,
not independently re-verified against Components 1 and 2's own code.

## 7. What comes next and why

Tier 2 (Tavily whitelist search) and the mechanical escalation between
tiers are next, deliberately kept as separate, later work on top of an
already-proven, already-committed Tier 1 — rather than building all of
tiered grounding in one pass and discovering a Tier-1-specific bug (like
either of the two found here) after Tier 2 already depends on it. If this
component's retrieval mechanism is subtly wrong in a way its own three
verification queries didn't catch — asymmetric embedding applied
inconsistently somewhere it wasn't checked, an edge case in chunking that
splits a load-bearing sentence awkwardly — the most likely place it would
first become visible is Component 4 (hypothesis generation), the first
component to actually use `retrieve_local`'s output as grounding context in
a real prompt. A retrieval result that looks plausible but is subtly
irrelevant wouldn't necessarily error there; it would show up as a
hypothesis whose stated rationale doesn't actually follow from its cited
grounding — exactly the kind of thing Sacred Gate 2's own citation
requirements exist to catch downstream, even if this component's own
testing didn't happen to surface it first.
