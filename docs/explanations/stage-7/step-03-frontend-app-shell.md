# Step 3 — Component 3, The Frontend App Shell

## 1. What this does

Everything before this component was Python. `docs/plans/stage-7-plan.md`
names Component 3 as: "Vite + React + TypeScript scaffold; Fathom's
tokens ported to a global stylesheet; theme handling (the same
dark-first, `prefers-color-scheme`-aware pattern the artifact already
proves); routing skeleton; a typed API client generated from the
backend's own response shapes." This component builds exactly that — a
new `frontend/` application, running on Vite's dev server, that renders
Fathom's real design system, switches between light and dark correctly,
navigates between a handful of placeholder pages, and can make one real,
fully-typed call to the live FastAPI backend and render what comes back.

**What this is not.** It is not the charter creation flow (Component 4),
the research log (Component 5), the trace drill-down (Component 6), or
the scoreboard (Component 7) — every route past the shell itself is an
explicit placeholder, not a partial implementation. It does not add or
change a single line of backend code. And the one page that *does* call
the real backend (`ChartersPage.tsx`) is a deliberate plumbing proof, not
a first draft of Component 5's actual UI — Section 3 explains why that
distinction matters.

New: the entire `frontend/` directory (a separate npm project, sibling to
`src/`/`tests/`/`docs/`), `.claude/launch.json`, and a new "Frontend
setup" section in `CLAUDE.md`.

## 2. Every meaningful line explained

### Where the code lives, and why that took zero lines of Python config to arrange

`frontend/` sits next to `src/`, not inside it. `pyproject.toml`'s
`[tool.setuptools.packages.find] where = ["src"]` tells setuptools
exactly one place to look for Python packages — a Vite/React project
(its own `package.json`, `node_modules/`, `tsconfig.json`, an entirely
separate dependency graph and build tool) has no business anywhere near
that discovery path. Putting it under `src/` would have meant either
setuptools silently trying to treat `frontend/node_modules/` as
candidate Python packages, or writing exclusion rules that don't
currently exist and have no other reason to. A sibling directory needs
none of that — it's just never looked at by anything Python-side.

### The TypeScript version conflict — a real bug, not a hypothetical

```
peer typescript@"^5.x" from openapi-typescript@7.13.0
Found: typescript@6.0.3
```

`npm create vite@latest frontend -- --template react-ts` installed
whatever it considers "latest" at scaffold time — in this environment,
genuinely `typescript@6.0.3`, a real major version, not a typo. Adding
`openapi-typescript` (needed later in this same component) immediately
failed with a real `ERESOLVE` peer-dependency error: that package
declares support for `typescript@^5.x` only. Two paths existed.
`--legacy-peer-deps` would have silenced the error and installed anyway,
but it would prove nothing about whether `openapi-typescript` actually
*works* correctly against a major TypeScript version its own authors
haven't declared support for — the error would be gone, the risk would
not. Checked instead whether a genuinely current TypeScript 5 release
exists (`npm view typescript versions`, confirming `5.9.3` is a real,
recent, actively-published version, not an ancient fallback), and pinned
`frontend/package.json`'s `typescript` devDependency to `~5.9.3` instead
of accepting the scaffold's own default. This is the same category of
fix `CLAUDE.md`'s own pgvector workaround and migration `ac225385b472`'s
`server_default` fix already are: a tool's "latest" or "autogenerated"
default didn't match what the actual dependency graph needed, and the
fix is to align with what's real rather than paper over the mismatch
with a flag that only suppresses the symptom.

### Porting Fathom's CSS — and deliberately not porting its JavaScript

Before writing a single line of `frontend/src/styles/fathom.css`, I
fetched and read the **entire** published Fathom artifact — all 549
lines, not just `docs/plans/stage-7-plan.md`'s summary of it — because
the plan's own claim ("Fathom's tokens are already real, working CSS
custom properties") is a factual claim about a specific external file,
and porting it faithfully required checking that claim against the
actual content rather than trusting the description of it.

Most of that file's `<head>` turned out to be a large, minified
JavaScript blob — Claude's own Artifact-viewer sandbox and frame-runtime
code: `postMessage` wiring between the artifact and its parent frame,
theme-sync handling, DOM-patching machinery for live edits. None of it
belongs in a real, standalone application; it references `parent` frame
origins and viewer-specific message contracts that only make sense
inside Claude's own iframe sandbox. Only the artifact's own `<style>`
block — the CSS custom properties, base styles, and component classes
(`.pill`, `.card`, `.stat-tile`, `table.board`, the trace-draw-on
animation) — is the actual, reusable design system, and that's what got
ported, verbatim, into `fathom.css`. The artifact's own documentation
classes (`.hero`, `.swatch-*`, `.type-row`, `.motion-demo`,
`footer.page-foot`) were left out on purpose too — those exist to
*describe* the design system to a human reading the artifact page; they
are not components the real app will ever render.

### `useTheme.ts` — the JavaScript half a real app has to supply for itself

```ts
useEffect(() => {
  if (override === null) {
    delete document.documentElement.dataset.theme
  } else {
    document.documentElement.dataset.theme = override
  }
}, [override])
```

The published artifact's own theme cascade (bare `:root` = dark,
`@media (prefers-color-scheme: light) :root:not([data-theme="light"])`
= system light with no override, `:root[data-theme="light"|"dark"]` =
an explicit override that wins either direction) is real, working CSS —
but *inside the artifact*, the `data-theme` attribute it keys off is set
by Claude's own Artifact-viewer host (the frame-runtime's `Q()` function,
reacting to `__frame_theme` messages from the parent). A standalone app
has no parent frame calling in to manage that attribute for it, so this
hook is the piece that has to exist to make the exact same CSS actually
function outside that sandbox: read the stored override (if any) on
mount, apply or remove `data-theme` to match, and expose a `toggle()`
that flips it.

```ts
const toggle = useCallback(() => {
  const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches
  const currentlyDark = override === 'dark' || (override === null && prefersDark)
  setOverride(currentlyDark ? 'light' : 'dark')
}, [override, setOverride])
```

`toggle` has to know the *effective* current theme, not just the stored
override, because the override can legitimately be `null` (following the
system). If it only checked `override === 'dark'`, a user whose system
is dark with no override set would click "switch to light" and see
nothing happen — the code would compute `currentlyDark = false` (since
`override` is `null`, not `'dark'`), and toggle *to* dark, which is
already what's showing. Reading `prefers-color-scheme` directly at
toggle time is what makes the button's behavior match what the user
actually sees on screen.

```ts
try {
  localStorage.setItem(STORAGE_KEY, next)
} catch {
  // Private browsing / storage disabled -- ...
}
```

Wrapped in `try`/`catch` rather than left to throw, because
`localStorage` can genuinely be unavailable (private browsing in some
browsers, storage explicitly disabled) — and a failed write there should
degrade to "the choice doesn't survive a reload," not crash the toggle
button for the rest of the session.

### The generated API client — the component's single most load-bearing decision

```ts
export const client = createClient<paths>({ baseUrl })
```

`paths` comes from `frontend/src/api/schema.gen.ts`, produced by running
`openapi-typescript` against the real, running FastAPI backend's own
`/openapi.json` — not hand-written TypeScript interfaces someone
inspected `src/api/schemas.py` to write. The alternative (hand-typing
`interface CharterOut { id: string; mandate_text: string; ... }` to
match the Pydantic model by eye) would satisfy the letter of "a typed API
client" but not its actual purpose: `docs/plans/stage-7-plan.md`'s own
reasoning for choosing TypeScript at all is that "typing the API client
against that shape is what catches a frontend/backend drift at build
time instead of at runtime" — and a hand-maintained type only catches
that drift if a human remembers to update both sides every time a
backend response model changes. A generated type has no such dependency
on memory: it is either regenerated (and therefore automatically
correct) or visibly stale because nobody ran the generator, never
silently wrong in between. `openapi-fetch` (not a hand-rolled `fetch`
wrapper around the generated types) is the same maintainer's sibling
package, built specifically to consume `openapi-typescript`'s exact
output — every path, method, and response shape is typed with zero
per-endpoint code written here, and a backend route added in a later
component needs nothing on this side beyond re-running the one generator
command.

```ts
const baseUrl = import.meta.env.VITE_API_BASE_URL ?? 'http://localhost:8000'
```

One named override point, defaulting to exactly where every prior
stage-7 live verification (Component 1's read-endpoint checks,
Component 2's real-LLM correction test) already ran the backend. A
future deployed build changes one environment variable here, not this
file.

The generated file itself is **committed to git**, not gitignored — an
explicit choice you made when asked directly, not one I made
unilaterally. The alternative (gitignore it, regenerate automatically on
`npm install` or `npm run dev`) would mean the backend has to be up,
reachable, and CORS-permissive before the frontend can typecheck or
build even once — including in a future CI environment that has no
reason to run the Python backend just to lint TypeScript. Committing it
means `npm install` alone is enough, the same way a committed lockfile
is. The honest cost, stated in `CLAUDE.md`'s own new setup section: a
stale committed file can only be caught by it disagreeing with real
usage later, not by any automated staleness check — regenerating it is a
manual step whenever a backend route changes.

### Routing — a library, not a hand-rolled path matcher

React ships no router of its own. Hand-rolling one (branching on
`window.location.pathname`, matching against a list of patterns) would
be re-solving a problem `react-router-dom` has already solved
thoroughly, for the same reason this project already builds its
backtester on `backtesting.py` rather than from scratch — a well-tested,
dominant library beats a bespoke reimplementation of the same
mechanics, especially for something as easy to get subtly wrong as path
matching, nested layouts, and browser history integration.

```tsx
<Route element={<Layout />}>
  <Route index element={<MandatePage />} />
  <Route path="charters" element={<ChartersPage />} />
  <Route path="charters/:charterId" element={<CharterDetailPage />} />
  <Route path="scoreboard" element={<ScoreboardPage />} />
</Route>
```

One shared parent route (`Layout`, rendering the persistent header/nav
via `<Outlet/>`) wrapping every page route, rather than each page
re-rendering its own header. This is the literal definition of an "app
shell" — the chrome that's the same on every page, built once.

### `ChartersPage.tsx` — a plumbing proof, explicitly not Component 5's real UI

This page's whole reason to exist is closing an item Components 1 and 2
left **open and named as a guess**: `src/api/app.py`'s CORS middleware
allows `http://localhost:5173` with a comment stating plainly that this
is "an educated guess... verify the first time Component 3's frontend
makes a real request here." This page is that verification, not
incidental early work on Component 5's actual research log. It reuses
the `.pill` component for a plain confirmed/unconfirmed boolean, which
is a real, disclosed looseness — `.pill`'s color vocabulary
(confirmed/rejected/inconclusive/decayed) was designed for a *verdict's*
outcome, not a charter's confirmation flag, and this page borrows it
anyway because the whole page is a stub Component 5 replaces entirely,
not a permanent interface decision anyone needs to defend later.

## 3. Design decisions and rejected alternatives

### The API client is generated, never hand-typed

Covered in depth in Section 2 — restated here because it's the
component's most consequential choice. **Chosen:** `openapi-typescript`
+ `openapi-fetch` against the backend's live schema. **Rejected:**
hand-written TypeScript interfaces mirroring the Pydantic models.
**Why:** a hand-typed interface is a promise a human has to keep every
time the backend changes; a generated one is a promise the toolchain
keeps automatically. **Cost to reverse:** low mechanically (delete the
generator, write interfaces by hand) but would reintroduce exactly the
silent-drift risk this choice exists to close.

### TypeScript pinned to `~5.9.3`, not the scaffold's own `6.0.2` default

**Chosen:** override the Vite template's default TypeScript version.
**Alternative considered:** `npm install --legacy-peer-deps` to force
past the conflict and keep whatever the scaffold picked. **Why
rejected:** that flag makes the *error message* disappear without
answering the actual question — does `openapi-typescript` correctly
process a `6.x` TypeScript AST it was never tested against? Rather than
gamble on an unverified combination for a tool this project depends on
for a genuinely important guarantee (drift-proof types), stepping back
to the latest release of the major version the tool actually declares
support for is a real fix. **Cost to reverse:** trivial — one version
string — but there's no real reason to, since nothing in this app's own
code needs TypeScript 6 specifically.

### `react-router-dom`, not a hand-rolled router

Covered in Section 2. **Chosen:** the established library. **Rejected:**
hand-rolled path matching. **Why:** a comparably solved problem to
backtesting-engine mechanics, which this project already refuses to
reinvent for the identical reason. **Cost to reverse:** moderate — every
route definition and every `useParams`/`NavLink` call site would need
rewriting — but there's no real driver to reverse it; nothing about this
project's routing needs exceeds what the library already does simply.

### One shared `Layout` route wrapping every page, not per-page chrome

**Chosen:** a single `<Layout>` component rendering the header/nav once,
with every page rendering only its own content inside `<Outlet/>`.
**Alternative considered:** each page component renders its own copy of
the header. **Why rejected:** the header (wordmark, nav links, theme
toggle) is identical on every page by definition — duplicating it per
page would mean five places to keep the nav's active-link logic and
theme toggle consistent instead of one, and the very first page added in
Component 4 would already need to copy code that already exists.
**Cost to reverse:** low, but there's no reason to prefer duplication.

### `ChartersPage.tsx` is scoped as a proof, not Component 5's first draft

**Chosen:** a minimal page that fetches and renders real data, explicitly
documented in its own file as a stand-in Component 5 will fully replace.
**Alternative considered:** treat this as a legitimate first pass at the
real research-log UI, since the plumbing has to be proven somewhere
anyway. **Why rejected:** conflating "prove the wiring works" with
"design the real UI" would mean Component 5 either inherits design
decisions (like the misused `.pill` semantics) made under a completely
different goal, or has to consciously discard work done here — cleaner
to name this page's job precisely and let Component 5 start from a real
design pass, the same "explain before writing" discipline this whole
project runs on. **Cost to reverse:** none — this file is meant to be
deleted or rewritten wholesale when Component 5 starts.

## 4. Concepts introduced

**An Artifact's runtime sandbox versus the design content it hosts.**
The published Fathom artifact is two genuinely different things stapled
together in one HTML file: Claude's own Artifact-viewer frame-runtime
(postMessage wiring, theme-sync, edit-patching — infrastructure for
running *inside* Claude's viewer) and the actual Fathom design system
(CSS tokens and components, which have nothing to do with being hosted
in an iframe). Porting "the artifact" correctly meant recognizing that
distinction and taking only the second half — treating the whole file as
one undifferentiated blob to copy would have pulled in code that is not
merely unnecessary but actively broken outside its sandbox (it posts
messages to a `parent` frame that, in a standalone app, does not exist
and is not listening).

**Peer dependencies as a compatibility contract, not a suggestion.**
`openapi-typescript@7.13.0` declaring `peerDependencies: { typescript:
"^5.x" }` is the package author stating exactly which TypeScript
versions they've built and tested against — npm's `ERESOLVE` error when
that's violated is npm correctly refusing to guess whether an untested
combination works. Overriding it with `--legacy-peer-deps` doesn't
answer that question; it just stops npm from asking it.

## 5. How this component's verification was satisfied

**Static checks:** `npx tsc -b --force` — zero errors. `npm run build`
(`tsc -b && vite build`) — succeeded, producing a real production
bundle.

**Live, in the browser, against the real running FastAPI backend — no
mock, per this stage's own stated verification standard:**
- First load: dark theme rendered with the real Fathom tokens (true
  black surface, Fraunces serif title, amber active-nav state) —
  confirming the ported CSS actually cascades correctly as authored.
- `/charters`: a real `GET` request (confirmed via
  `read_network_requests` showing `200 OK`, fired twice — React
  `StrictMode`'s deliberate double-invocation of effects in development,
  expected and harmless, not a bug) returned and rendered six real rows
  from the actual dev database, including the same charter
  (`15bc2076-...`) Component 1's own live verification used. This is the
  moment the CORS guess from Components 1–2 got tested for real, and it
  passed on the first try.
- Clicking a charter row navigated to `/charters/:charterId` with the
  real id resolving correctly via `useParams` — dynamic routing proven
  against a real value, not a hardcoded test route.
- The theme toggle flipped the entire page to light mode correctly
  (including the confirmed-status pill's separately-defined light-mode
  color), and the override survived a full page navigation — proving
  the `localStorage` half of `useTheme` actually persists, not merely
  that the CSS half renders correctly once.
- With the stored override cleared and the Browser tool's
  `resize_window` `colorScheme` emulation, both
  system-preference-light-with-no-override and
  system-preference-dark-with-no-override rendered correctly — exercising
  the actual `@media (prefers-color-scheme: light)` branch of the CSS
  cascade, not only the explicit-override branch a manual toggle click
  would exercise on its own.
- The backend's full test suite was reconfirmed green throughout
  (377/377) — expected, since this component touches zero backend code,
  but checked rather than assumed.

**What this does not prove.** `openapi-fetch`'s behavior against error
responses was written (`ChartersPage.tsx`'s `error` branch) but never
live-exercised against an actually-unreachable backend — the "Could not
reach the backend" message has not been seen to actually appear. Nothing
here was checked on a real mobile viewport, only desktop. And none of
this proves anything about Components 4–7's real page content, since
none of it exists yet — this component proves the shell it will live
inside works, not that the pages themselves will be right.

## 6. Interview defense

**"Why generate the API types instead of just writing them by hand —
isn't that adding a build step for something a competent developer could
type out in ten minutes?"** Because the ten minutes it takes to hand-type
them is also exactly the ten minutes it takes for them to start drifting
the first time a backend response model changes and nobody remembers to
update the frontend's copy. `docs/plans/stage-7-plan.md`'s own stated
reason for using TypeScript at all is catching that drift at build time
— a hand-maintained type is a weaker version of that same promise,
because it depends on someone's memory instead of a regeneration step.
The "build step" is one npm script, and it already caught nothing wrong
this time — but the whole point is that it *would* catch something the
moment a real mismatch existed.

**"Why didn't you just use `--legacy-peer-deps` when the TypeScript
version conflict came up? Everyone does that."** Because it would have
answered the wrong question. The error wasn't cosmetic — it was npm
correctly reporting that `openapi-typescript`'s authors have not tested
or declared support for TypeScript 6.x. Forcing the install past that
warning makes the warning disappear without making the underlying
combination any more verified than it was before. Pinning to the latest
TypeScript 5 release instead means the exact combination the tool's own
authors built and tested against is what's actually running.

**Hard question: "You verified the theme toggle, routing, and one real
API call. You didn't verify error handling, mobile layout, or anything
close to what a real user session looks like. Isn't 'app shell
verified' overstating what you actually checked?"** That's fair, and
worth being precise about rather than glossing over: what's verified is
that the *infrastructure* — the design tokens rendering correctly in
both themes and both system-preference states, routing resolving real
dynamic values, and the generated client successfully round-tripping
real data through real CORS — actually works end to end, once, live. It
does not mean the app is production-ready or that every edge case has
been exercised; `ChartersPage.tsx`'s own error branch and any mobile
behavior are explicitly named here as unverified, not silently assumed
fine. The honest scope of this component's gate is "the pieces later
components will build on top of are real and working," not "this app is
finished being tested."

**"Why put the frontend in a completely separate top-level directory
instead of somewhere under `src/` where the rest of the code lives?"**
Because `src/` isn't "where the code lives" in general — it's
specifically what `pyproject.toml`'s `setuptools.packages.find` scans
for Python packages. A Vite/React project's `node_modules/` alone would
be an enormous, irrelevant tree for a Python packaging tool to have any
reason to look inside. Keeping them as fully separate sibling trees with
entirely separate toolchains is simpler than teaching either tool to
ignore the other's territory.

## 7. What comes next and why

Component 4 (the charter creation flow — the mandate textarea, the
confirmation screen, and Component 2's own correct/confirm round trip
made visible) is next, replacing `MandatePage.tsx`'s placeholder with the
real form. It inherits this component's generated client, theme system,
and shell layout directly — none of that needs rebuilding, only using.

**If this component were wrong** — if the generated types didn't
actually match the backend, or if CORS had failed, or if the theme
cascade had a gap — the failure would show up immediately and loudly the
moment Component 4 tried to build a real form against it: a type error
at compile time if the generated schema were wrong, a blocked network
request visible in the browser's console if CORS had failed, or a
broken-looking page in one theme if the cascade had a gap. That
immediacy is exactly why this component's own verification ran against
the real backend rather than stopping at "it type-checks" — a shell that
only *looks* wired up but silently fails the first time something real
flows through it would have pushed this exact category of bug one
component later, onto work that has an actual user-facing feature to
get right at the same time.
